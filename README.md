# QA Test Skills - 软件测试技能集

> 45个专家级测试技能，覆盖测试全生命周期

## 项目背景

### 解决什么问题？

初级测试人员使用AI时，只会问"帮我生成XX模块的测试用例"，AI不知道上下文和背景，回答也很宽泛，导致AI辅助测试效果不佳。

### 我们的方案

**用户提问方式不变**，技能集在后台帮他完成专家级测试设计：
- 构建业务上下文
- 挖掘隐性需求
- 识别风险区域
- 生成结构化用例
- 评审和补盲

### 核心价值

- **零学习成本**：用户无需改变现有习惯
- **专家级输出**：资深测试经验编码为可加载技能
- **完整追溯链**：需求→场景→用例→评审，全程可追溯
- **持续优化**：专家评审+元学习，越用越好

## 与其他Skills的区别

### 设计理念对比

| 维度 | 通用测试Skills | 我们的Skills |
|------|--------------|-------------|
| **核心目标** | 生成完整的测试用例（含步骤） | 帮用户思考"测什么"，而非"怎么测" |
| **生成内容** | 用例+步骤+预期结果 | 用例概览（编号/类型/标题/级别/风险） |
| **不生成内容** | 无 | 详细测试步骤（避免AI幻觉） |
| **价值定位** | 替代测试人员思考 | 辅助测试人员思考 |

### 为什么不生成详细测试步骤？

**核心原因：详细步骤与业务强关联，AI容易产生幻觉**

```
用户输入："帮我生成登录的测试用例"
    │
    ▼
AI知道的：登录功能的一般性测试点
    │
    ├── ✅ 可以生成：测试场景、边界条件、风险点
    └── ❌ 不适合生成：具体操作步骤（不知道业务实现）
```

**具体步骤需要的上下文**：
- 系统界面布局
- 操作流程细节
- 业务规则实现
- 技术实现方式

**这些信息在用户简单提问时是缺失的**，AI强制生成步骤会导致：
- 步骤与实际系统不符
- 预期结果不准确
- 测试人员需要大量修正

### 我们的价值定位

```
┌─────────────────────────────────────────────────────────────┐
│  技能集的价值是帮用户思考"测什么"，而非"怎么测"              │
├─────────────────────────────────────────────────────────────┤
│  第1层：测什么场景          ← ✅ 已覆盖                      │
│  第2层：每个场景的边界      ← ✅ 已覆盖                      │
│  第3层：风险和优先级        ← ✅ 已覆盖                      │
│  第4层：具体操作步骤        ← ❌ 不覆盖（需要业务上下文）    │
└─────────────────────────────────────────────────────────────┘
```

### 适用场景

| 场景 | 适合使用 | 说明 |
|------|---------|------|
| 需求评审前 | ✅ | 快速了解测试点 |
| 用例设计时 | ✅ | 补充遗漏场景 |
| 用例评审时 | ✅ | 验证覆盖完整性 |
| 用例执行时 | ⚠️ | 需要补充具体步骤 |

### 防幻觉机制

| 机制 | 说明 |
|------|------|
| 输入验证 | 确保用户输入包含足够信息 |
| 事实核查 | 验证AI输出是否基于真实信息 |
| 一致性检查 | 验证需求/风险/场景是否匹配 |
| 可执行性验证 | 验证输出是否可实际执行 |

## 如何使用

### 安装

```bash
# 克隆仓库
git clone https://github.com/Kokxi/qa-test-skills.git

# 安装插件
/plugin dir ./qa-test-skills
```

### 快速开始

```bash
# 直接输入需求，自动执行完整工作流
帮我生成购物车模块的测试用例

# 上传需求文档
[上传PRD文档] 帮我生成测试用例

# 给URL链接
https://xxx.com/api-docs 帮我生成接口测试用例
```

### 单独使用技能

```bash
# 需求解构
帮我解构这个需求：[需求描述]

# 边界分析
帮我分析这个场景的边界：[场景描述]

# Bug报告
帮我写Bug报告：[Bug描述]
```
