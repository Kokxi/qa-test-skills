# 接口测试工具选型

> 本文是 `qa-api-testing` 的**工具参考**。需要选型、或要展开某工具的能力边界时读本文；
> 没有特殊约束时直接用 `SKILL.md` 的默认选型表即可，不必读本文。

## 默认选型（无特殊约束时直接用这套）

| 场景 | 默认工具 | 理由 |
|------|---------|------|
| 日常调试与文档 | Postman / Apifox | 上手最快，团队协作与接口文档一体 |
| 自动化执行 | **pytest + requests**（Python 栈）/ REST Assured（Java 栈） | 生态成熟、易接 CI |
| 契约测试 | **Pact**（消费者驱动）/ Schemathesis（OpenAPI 校验） | 前者管协作方破坏性变更，后者管实现与契约一致 |
| 第三方与异常 Mock | **WireMock** | 延迟/超时/脏数据场景开箱即用 |
| 性能 | **k6**（脚本轻、CI 友好）；需 GUI 与分布式再选 JMeter | 压测不是本技能默认动作，按需引入 |

> 明确"单工具全栈"诉求时用 **Karate**（REST+GraphQL 自动化/契约/Mock 一体）。
> gRPC 用 grpcurl 调试；WireMock 无法覆盖流式语义，gRPC 流式用例要另配工具。

## 能力对照矩阵

| 工具 | 协议支持 | 自动化 | 契约测试 | Mock | 适用场景 |
|-----|---------|--------|---------|------|---------|
| **Postman/Apifox** | REST/GraphQL/WebSocket | 手动+脚本 | ❌ | ✅ | 接口调试、文档管理、小规模自动化 |
| **pytest+requests** | 通用HTTP | ✅ | ❌ | ❌ | Python项目API自动化、CI集成 |
| **REST Assured** | REST | ✅ | ❌ | ❌ | Java项目API自动化 |
| **Karate** | REST/GraphQL | ✅ | ✅ | ✅ | 全栈API测试（单工具方案） |
| **Pact** | REST/GraphQL | ❌ | ✅ | ✅ | 消费者驱动契约测试 |
| **Schemathesis** | REST(OpenAPI) | ✅ | ✅ | ❌ | 按 OpenAPI 契约自动生成并校验用例 |
| **WireMock** | 通用HTTP | ❌ | ❌ | ✅ | 第三方Mock、异常模拟 |
| **MockServer** | 通用HTTP | ❌ | ❌ | ✅ | 轻量级 Mock，易上手 |
| **grpcurl / gRPCui** | gRPC | 手动 | ❌ | ❌ | gRPC 接口调试（流式需专用工具） |
| **SOAP UI** | SOAP | ✅ | ✅ | ❌ | 按 WSDL 生成请求、校验报文结构 |

## 性能压测工具（性能维占 10%，按需引入）

| 工具 | 特点 | 适用 |
|------|------|------|
| **k6** | JS 脚本、CI 友好、依赖少 | 首选，尤其已有 CI 时 |
| **Locust** | Python 脚本、易造数 | Python 栈团队 |
| **JMeter** | GUI + 分布式、生态最广 | 需可视化配置或大规模分布式 |
| **wrk** | 极轻量基准工具 | 快速摸底，不做完整场景 |

> 性能用例见 [`test-cases.md`](test-cases.md) 第四节。无历史基准时先做基准测试建立基线，
> 再断言相对退化 < 20%；P95 < 500ms 为建议值，按业务场景调整。

## 选型时的三个常见坑

1. **用功能测试的工具去做契约测试**：Pact 和 Schemathesis 解决的是不同问题 —— 前者管
   "消费者会不会被我的变更打爆"，后者管"实现是否偏离契约"。做接口回归用 Schemathesis，
   做跨团队协作用 Pact。
2. **Mock 覆盖了真实行为**：WireMock 返回的响应是你自己写的，它证明不了真实下游的行为。
   第三方 Mock 只能验证"我方在下游异常时怎么表现"，不能替代真实联调。
3. **压测和功能测试混用同一套脚本**：功能脚本串行断言业务结果，压测脚本要的是高并发下的
   指标采样。混用两边都做不好。
