# 测试策略六要素详解

> 本文是 `qa-test-strategy-design` 的**方法详图**。需要逐要素展开、或要填具体数值时读本文；
> 只想知道策略该覆盖哪几块时读 `SKILL.md` 的六要素速查即可。

---

## 要素 1：项目背景评估

```text
评估维度：
├─ 项目阶段：新项目 / 迭代优化 / 维护阶段
├─ 团队规模：人员数量和经验水平
├─ 技术栈：技术复杂度和团队熟悉度
├─ 工期：开发周期和测试周期
└─ 历史质量：历史 Bug 密度和漏测率

评估结果：
- 项目阶段：[新项目/迭代/维护]
- 团队：[X 人，经验水平]
- 技术栈：[复杂度 + 团队熟悉度]
- 工期：[开发 X 周 / 测试 Y 周]
- 历史质量：[Bug 密度、漏测率]
```

> **"团队熟悉度"比"技术复杂度"更重要**。团队不熟的新技术栈，风险主要来自
> 理解偏差而非实现难度——这两类风险要用不同手段应对。

---

## 要素 2：风险分析

```text
风险识别：
├─ 业务风险：核心功能 / 资金 / 安全
├─ 技术风险：新架构 / 复杂逻辑 / 第三方
├─ 进度风险：工期紧 / 人员不足
└─ 质量风险：历史问题多 / 复杂度高
```

> **风险等级与测试深度的映射统一由 `qa-risk-intuition` 定义**（≥45 高→深测 /
> 15-44 中→常规 / ≤14 低→冒烟）。本技能**不重新定义阈值**，
> 直接引用上游评估结论——避免同一项目里出现两套风险口径。

---

## 要素 3：分层策略

```text
测试金字塔：
                ┌─────────┐
                │  E2E测试 │  10%
                ├─────────┤
                │ 接口测试 │  30%
                ├─────────┤
                │ 单元测试 │  60%
                └─────────┘

分层比例（按业务风险调整）：
├─ 单元测试：60-70%（核心逻辑，开发者自测）
├─ 接口测试：20-30%（业务流程，服务间契约）
├─ E2E 测试：10%（核心路径，成本最高）
└─ 探索测试：补充（复杂场景、自动化难覆盖的部分）
```

> **不要在 CI 里堆满慢的 E2E**。E2E 只跑核心路径，其余靠接口层拦截。
> 分层配比的具体落地（流水线卡点）交 `qa-ci-cd-testing`。

## 要素 4：手段选择

```text
自动化 vs 手动：
├─ 自动化：回归测试 / 冒烟测试 / 数据驱动
├─ 手动：探索测试 / 用户体验 / 兼容性
└─ 工具辅助：性能测试 / 安全测试 / 接口测试

选择依据：
- 重复执行 → 自动化
- 复杂判断 → 手动
- 数据驱动 → 自动化
- 探索性 → 手动
```

> 判断标准是**重复次数**与**结果确定度**，不是"这个功能重不重要"。
> 一次性的核心功能手工测完全合理；天天跑的边缘功能反而必须自动化。

---

## 要素 5：资源分配

```text
资源分配：
├─ 人力分配：测试人员角色和任务
├─ 时间分配：各阶段测试时间
├─ 环境分配：测试环境准备
└─ 工具分配：测试工具准备

时间分配（参考值，按项目调整）：
- 需求分析：10%
- 用例设计：20%
- 测试执行：50%
- 回归测试：15%
- 报告总结：5%
```

---

## 要素 6：准入准出标准

```text
准入标准（可开始测试的前提）：
├─ 需求评审通过
├─ 开发自测通过
├─ 冒烟测试通过
├─ 测试环境就绪
└─ 测试数据准备

准出标准（可发布的门槛）：
├─ 用例执行率 ≥ 95%
├─ 用例通过率 ≥ 90%
├─ 高严重度 Bug 修复率 = 100%
├─ 中严重度 Bug 修复率 ≥ 90%
└─ 无阻塞性 Bug
```

> 上述百分比是**默认模板值**，不是行业标准。项目应根据历史数据校准：
> 一个长期执行率 100% 的团队，把准出定在 95% 等于形同虚设。
> 定得太松会让准出失去拦截作用，定得太严会逼着团队刷执行率。
> **每个项目应显式写出自己采用的值与依据。**
