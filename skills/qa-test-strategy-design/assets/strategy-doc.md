# 测试策略文档模板

> 复制下面整块板填写。六要素的评估方法见 [`six-elements.md`](six-elements.md)。

## 测试策略

**策略 ID**：STRAT-{模块缩写}-{三位序号}
**关联需求**：REQ-{模块缩写}-{序号}
**版本 / 日期**：v1.0 / YYYY-MM-DD

### 1. 项目背景

| 项 | 内容 |
|----|------|
| 项目阶段 | [新项目/迭代/维护] |
| 团队 | [X 人，经验水平] |
| 技术栈 | [复杂度 + 团队熟悉度] |
| 工期 | [开发 X 周 / 测试 Y 周] |
| 历史质量 | [Bug 密度、漏测率] |

### 2. 风险分析

> 风险等级直接引用 `qa-risk-intuition` 的结论（≥45 高→深测 / 15-44 中→常规 / ≤14 低→冒烟），
> 本策略不重新定义阈值。

| 风险等级 | 区域 | 测试深度 | 依据 |
|---------|------|---------|------|
| 高 | [如 支付/并发回调] | 深测 | RISK-PAY-CONC-002（125 分） |
| 中 | [如 订单/导出] | 常规 | RISK-ORDER-EXPORT-005（27 分） |
| 低 | [如 通知/推送] | 冒烟 | RISK-NOTIFY-PUSH-004（3 分） |

**本项目不测什么**（写明比不写更有价值）：
- [如：后台运营管理页面 —— 内部使用、无资金风险、不在本次迭代范围]

### 3. 测试范围

| 范围类型 | 内容 |
|---------|------|
| **测什么** | [功能模块清单 + 对应需求 ID] |
| **不测什么** | [明确排除项 + 原因] |
| **测到什么程度** | [深度定义：冒烟/常规/深测] |

### 4. 分层策略

| 层级 | 占比 | 覆盖内容 | 执行时机 |
|------|------|---------|---------|
| 单元测试 | 60% | 核心逻辑 | 开发者自测，提交时 |
| 接口测试 | 30% | 业务流程、服务间契约 | 提交后 / 每日 |
| E2E 测试 | 10% | 核心路径 | 发版前 |
| 探索测试 | 补充 | 自动化难覆盖部分 | 迭代中穿插 |

### 5. 手段选择

| 手段 | 范围 | 理由 |

| 手动 | [探索/体验/兼容性] | 需人工判断 |
| 工具辅助 | [性能/安全/接口] | [选择与理由] |

### 6. 资源分配

| 维度 | 方案 |
|------|------|

|------|------------|---------|------|

## 填写要求

| 项 | 要求 | 常见错误 |
|----|------|---------|
| 策略 ID | `STRAT-{模块缩写}-{三位序号}` | 用 `TC_` 或 `REQ-` 前缀 |
| 风险等级 | 引用 `qa-risk-intuition` 结论，不自己重算 | 本技能另定一套阈值 |
| **不测什么** | **必填**，写明排除项与原因 | 留空（等于没做取舍决策） |
| 分层占比 | 合计 100%；按业务风险可调但要说明 | 各层都是"重要"导致全是 100% |
| 准出标准 | 写本项目采用值 + 依据 | 照抄模板不校准 |
| 覆盖率 | 标注口径（如"基于现有需求文档"） | "全覆盖""100%" |

## 交付前自检

- [ ] 六要素全部有内容；简单项目可只覆盖 4 个但需说明省略原因
- [ ] 风险等级引用上游 `qa-risk-intuition`，未另立阈值
- [ ] **"不测什么"已明确写出**（策略的价值一半在这里）
- [ ] 分层占比合计 100%，且说明了偏离默认配比的理由
- [ ] 准出标准写明了本项目采用值与依据
- [ ] 关联需求 ID 格式为 `REQ-`
- [ ] 策略 ID 格式为 `STRAT-`
- [ ] 无"全覆盖/100%"绝对化表述
