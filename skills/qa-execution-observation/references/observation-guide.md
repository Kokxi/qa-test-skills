# 六路信号与异常识别详解

> 本文是 `qa-execution-observation` 的**观察手册**。需要逐路信号的观察要点与方法、
> 或要识别异常信号时读本文；只想知道本轮该看几路信号时读 `SKILL.md` 的速查表。

**为什么是六路**：测试执行不是"按步骤操作看结果"。**大多数 Bug 是被"不小心看到"的，
而不是被测出来的**——你得同时盯着六路信号，才有机会看到它们。

---

## 信号 1：功能结果（最基础）

```text
观察要点：
├─ 结果正确性：是否符合预期？
├─ 结果完整性：是否有遗漏？
├─ 结果一致性：多次执行结果一致吗？
└─ 结果边界：边界值处理正确吗？

观察方法：对比预期结果 / 多次执行验证 / 边界值测试
```

## 信号 2：性能信号（容易忽略）

```text
观察要点：
├─ 响应时间：比正常慢多少？
├─ 加载时间：页面加载耗时？
├─ 处理时间：后台处理耗时？
└─ 资源消耗：CPU/内存/网络占用？

观察方法：开发者工具 Performance 面板 / 接口耗时统计 / 资源监控
```

> 性能异常往往**不阻塞功能**，所以最容易漏。"功能对了"不等于"性能可以接受"。

## 信号 3：日志信号（关键线索）

```text
观察要点：
├─ ERROR 级别日志
├─ Exception 堆栈
├─ 慢查询日志
├─ WARN 级异常警告
└─ 重试/降级记录

观察方法：控制台 / 日志文件 / APM 平台
```

> **WARN 级别最容易被忽略**。功能正常但日志里有 WARN，往往说明有异常被"吞掉"了——
> 这类问题会在特定条件下放大成线上事故。

## 信号 4：数据信号（验证结果）

```text
观察要点：
├─ 数据是否正确写入？
├─ 关联数据是否一致？
├─ 字段值是否正确（精度/格式/时区）？
└─ 脏数据是否残留？

观察方法：直接查库 / 查接口返回 / 对账
```

> 数据信号是**最可靠**的一路：界面可以骗人，数据库不会。
> 前端显示对了但库存没扣，这种只有查库才看得见。

## 信号 5：前端信号（用户视角）

```text
观察要点：
├─ 渲染是否正确？
├─ 交互是否正常？
├─ 样式是否错乱？
└─ 控制台是否有报错？

观察方法：手动操作观察 / 浏览器 DevTools / 多浏览器测试
```

## 信号 6：依赖信号（外部影响）

```text
观察要点：
├─ 第三方接口：调用成功吗？
├─ 下游服务：响应正常吗？
├─ 消息队列：消息发送成功吗？
├─ 缓存服务：缓存读写正常吗？
└─ 外部资源：CDN/图片加载正常？

观察方法：查看网络请求 / 检查接口调用 / 监控依赖服务
```

## 异常信号识别速查

| 信号路 | 异常信号 |
|-------|---------|
| 功能 | 返回错误码 / 返回空数据 / 返回格式错误 / 响应超时 |
| 性能 | 响应时间突增 / 页面加载缓慢 / 后台处理超时 / 资源占用过高 |
| 日志 | ERROR 日志 / Exception 堆栈 / 慢查询 / 异常 WARN |
| 数据 | 数据未写入 / 数据不一致 / 格式错误 / 数据丢失 |
| UI | 白屏 / 卡顿 / 样式错乱 / 控制台报错 |
| 依赖 | 接口调用失败 / 服务不可用 / 消息发送失败 / 缓存读写失败 |

## 异常处理引导

| 场景 | 表现 | 处理方式 |
|------|------|---------|
| **异常无法复现** | 观察到问题但再次操作不出现 | 记录环境与完整操作序列，标记为**间歇性问题**（往往是时序/并发 Bug，务必提交） |
| **日志信息不足** | 日志被截断/未开启 | 建议开发补日志；用抓包工具补充信号；交 `qa-testability-advocacy` 推动可观察性 |
| **依赖服务不可用** | 依赖服务挂了 | 记录故障现象；用 Mock 模拟依赖继续测；**不要把它当成本功能的 Bug** |
| **性能不达标但非代码问题** | 响应超阈值 | 排查环境因素（网络/数据量/并发），标注基线；确认后再判是否缺陷 |
| **环境问题 vs 缺陷** | 现象像 Bug | **先分流再定性**：看错误栈最深处服务名；是环境就记 `environment_issues` 不提缺陷单 |

> **最容易犯的错**：把环境问题当缺陷提，或把缺陷当环境问题放过。
> 两者都会污染缺陷库、误导团队。分流规则见上表最后一行。
