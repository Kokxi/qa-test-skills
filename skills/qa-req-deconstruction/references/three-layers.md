# 需求三层次挖掘详解

> 本文是 `qa-req-deconstruction` 的**挖掘方法**。需要展开某一层的完整清单、或不知道隐性需求怎么挖时读本文；
> 只想知道三层各占多少、用什么方法时读 `SKILL.md` 的速查表即可。

**为什么要分层**：无论需求文档写得多详细，解构之后总能发现盲区。层的区别是"来源"——
显性来自文档，隐性来自追问，衍生来自推导。

---

## 第 1 层：显性需求 —— 文档明确写出的

```text
提取方法：
1. 逐条阅读需求文档
2. 标注每条需求的关键词
3. 分类整理：功能需求 / 非功能需求 / 约束条件
4. 输出：显性需求清单（每条带 REQ-{模块缩写}-{序号}）
```

**检查**
- [ ] 所有功能点已提取？
- [ ] 所有约束条件已提取？（约束条件最常被当正文略过）
- [ ] 所有非功能需求已提取？（性能/安全/合规要求）
- [ ] 每条需求**可测试**？"系统要快"不可测，"P95 < 500ms"可测

> 判据：如果一条"需求"没法写出一条测试用例，它就不是需求，是愿望。

---

## 第 2 层：隐性需求 —— 文档没写但隐含的

**这是本技能的核心价值所在。** 隐性需求占总量 30-35%，且**几乎从不写在文档里**。

### 五问法

```text
1. 对每个"应该"问"如果不呢？"     → 依赖项缺失
2. 对每个"正常"问"异常呢？"       → 错误处理
3. 对每个"确定"问"假设呢？"       → 外部依赖的不确定性
4. 对每个"存在"问"不存在呢？"     → 空态与首次
5. 对每个"并发"问"同时操作呢？"   → 竞态与资源竞争
```

### 八类隐性需求

```text
├─ 业务隐含：业务流程的隐含步骤        （下单后要不要发通知？谁来发？）
├─ 技术隐含：技术实现的隐含约束        （超时/重试/幂等由哪一层保证？）
├─ 用户隐含：用户行为的隐含假设        （用户会看错误提示吗？会重试吗？）
├─ 环境隐含：运行环境的隐含条件        （测试环境能不能模拟支付回调？）
├─ 数据隐含：数据状态的隐含变化        （数据存哪？谁是主数据？）
├─ 并发隐含：并发操作的隐含冲突        （两人同时改同一条会怎样？）
├─ 时序隐含：操作顺序的隐含依赖        （A 必须在 B 之前，反了呢？）
└─ 异常隐含：异常情况的隐含处理        （异常后数据处于什么状态？能恢复吗？）
```

**检查**
- [ ] 库存相关隐性需求（超卖、占用、释放）
- [ ] 并发相关隐性需求（竞态、重复提交）
- [ ] 时序相关隐性需求（顺序依赖、竞态窗口）
- [ ] 异常处理隐性需求（恢复能力，不只是"报错了"）
- [ ] 数据一致性隐性需求（跨模块读写同一份数据）
- [ ] 安全相关隐性需求（越权、注入、敏感信息）

> **最常见的漏测**：异常处理只验证了"报错了"，没验证"之后系统还能不能用"。

## 第 3 层：衍生需求 —— 从前两层推导出的

```text
推导方法：
1. 从用户角色推导：不同角色有什么需求？
2. 从使用场景推导：不同场景有什么需求？
3. 从边界条件推导：极端情况有什么需求？
4. 从关联功能推导：相关功能有什么需求？
5. 从数据流向推导：数据在模块间怎么流？
```

**推导示例**
- 显性："密码至少 8 位" → 隐性：密码强度规则？允许特殊字符吗？历史密码能否复用？
- 显性："发送验证码" → 隐性：有效期多久？发送频率限制？错误次数上限？换绑手机号后旧码还有效吗？
- 显性："导入 Excel" → 衍生：导出功能是否也需要？导入失败能否回滚？重复导入如何处理？

**检查**
- [ ] 不同用户角色需求已推导？（同一功能不同角色往往要求不同）
- [ ] 不同使用场景需求已推导？
- [ ] 边界条件需求已推导？
- [ ] 关联功能需求已推导？（做了 A，是否必须做 B？）
- [ ] 数据流向需求已推导？

> **衍生必须标 `[待确认]`**：没有场景支撑的衍生就是脑补。标出来让人确认，
> 而不是混进需求表里当既定事实。

## 常见反模式

1. **顺手牵羊**：解构时就开始设计测试用例
   → 解构只做需求分析，不提前跳入测试设计。用例是 `qa-scenario-tree` 之后的事

2. **隐藏不标**：隐性需求挖掘出来却不标注
   → 每条隐性/衍生需求必须带标识（`[推断]` / `[假设]` / `[待确认]`），
   否则下游无法区分"文档要求的"和"我猜的"

3. **规则遗漏**：只拆需求不拆规则
   → 每条需求必须连带提取对应的业务规则，规则用 `RULE-{类型}-{序号}`

4. **过度衍生**：衍生需求推导到不切实际
   → 必须有合理场景支撑，否则标 `[待确认]`

5. **五维偏科**：只做输入/操作拆解，忽略状态/输出/规则
   → 五维必须完整使用，不可选择性跳过（详见 `five-dimensions.md`）
