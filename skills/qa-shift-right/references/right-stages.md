# 右移三阶段详解

> 本文是 `qa-shift-right` 的**方法详图**。需要展开某一阶段、挑选监控工具或混沌工程工具时读本文；
> 只想知道右移分哪几个阶段、每阶段管什么时读 `SKILL.md` 速查即可。

**⚠️ 灰度策略与回滚条件由 `qa-release-risk-governance` 统一定义**，本技能不重复维护。
需要设计灰度放量阶梯或回滚阈值时，读那个技能的方案；本文件只讲"上线之后怎么持续验证"。

---

## 阶段 1：灰度发布后的验证

灰度策略本身（放量阶梯、灰度维度选择、回滚条件）见 `qa-release-risk-governance`。
本技能关注的是**灰度期间要盯什么**：

```text
灰度监控指标：
├─ 业务指标
│   ├─ 订单量 / 交易量
│   ├─ 转化率 / 成功率
│   └─ 用户活跃度
│
├─ 技术指标
│   ├─ 错误率 / 异常率
│   ├─ 响应时间 / 吞吐量
│   └─ 资源使用率（CPU/内存）
│
└─ 用户反馈
    ├─ 投诉量
    ├─ 客服咨询量
    └─ 社交媒体反馈
```

> **三类指标都要看**。只看技术指标会漏掉"功能能跑但结果不对"（比如金额算错，
> 不报错但业务指标下滑）；只看业务指标会漏掉"当前没影响但已在积累风险"（内存泄漏）。

## 阶段 2：线上监控体系

```text
监控体系：
├─ 业务监控
│   ├─ 核心业务指标（订单量、成功率、转化率）
│   ├─ 业务流程监控（关键路径是否走通）
│   └─ 业务异常告警
│
├─ 技术监控
│   ├─ 应用性能监控（APM）
│   ├─ 基础设施监控（CPU/内存/磁盘/网络）
│   ├─ 日志监控（ERROR/WARN 聚合）
│   └─ 链路追踪（跨服务调用链）
│
└─ 用户体验监控
    ├─ 前端性能监控（首屏、加载）
    ├─ 用户行为分析（埋点）
    └─ 用户反馈收集（客服工单、应用商店评论）
```

### 监控工具参考

> 具体选型请结合团队技术栈与云厂商，下面是常见选项。

| 类别 | 工具 | 说明 |
|------|------|------|
| **APM** | SkyWalking / Pinpoint / Jaeger / Zipkin | 分布式链路追踪与调用耗时 |
| **日志** | ELK Stack / Loki / Splunk | 集中日志与全文检索 |
| **告警** | Prometheus + Alertmanager / Grafana / PagerDuty | 指标采集、告警规则、值班通知 |
| **前端体验** | Sentry | 前端异常采集与聚合 |
| **用户行为** | Mixpanel / 神策 | 埋点分析 |

## 阶段 3：混沌工程

### 四项原则

```text
├─ 稳态假设：系统在故障下应保持稳态（先定义"正常"长什么样）
├─ 爆炸半径：控制故障影响范围
├─ 持续实验：持续验证系统韧性，而非一次性演练
└─ 自动化：故障注入与恢复判定都应自动化
```

### 故障类型

```text
├─ 基础设施故障
│   ├─ 网络延迟 / 丢包
│   ├─ 节点宕机
│   ├─ 磁盘故障
│   └─ CPU / 内存压力
│
├─ 应用层故障
│   ├─ 服务不可用
│   ├─ 接口超时
│   ├─ 数据库故障
│   └─ 缓存故障
│
└─ 业务层故障
    ├─ 第三方服务故障
    ├─ 数据不一致
    └─ 流量突增
```

### 混沌工程工具

| 工具 | 用途 | 适用环境 | 特点 |
|------|------|---------|------|
| Chaos Monkey | 随机终止实例 | AWS | Netflix 开源，最简 |
| Chaos Mesh | K8s 故障注入 | Kubernetes | 功能全面，社区活跃 |
| Litmus | 云原生混沌工程 | Kubernetes | CNCF 项目 |
| Gremlin | 商业混沌工程平台 | 多云 | 企业级支持 |

> **混沌工程的执行前提**（硬约束，不可跳过）：
> 1. 获得组织书面授权
> 2. 先在非生产/影子环境验证
> 3. 逐步扩大爆炸半径
> 4. 必须有熔断与自动回滚
> 5. **禁止未经审批在生产环境直接执行混沌实验**

## 用户反馈闭环

```text
反馈收集渠道：
├─ 应用商店评论
├─ 客服工单
├─ 应用内反馈入口
├─ 社交媒体 / 社区
└─ 埋点行为异常（用户静默流失）

闭环要求：
├─ 每条反馈打标（功能缺陷 / 体验问题 / 数据问题 / 误报）
├─ 缺陷类转 qa-bug-reporting
├─ 体验类进产品需求池
└─ 误报类回写监控规则，避免噪声
```

> **"误报类回写监控规则"是常被忽略的一步**：不处理误报，告警会越来越钝，
> 最终团队开始无视告警——这是线上监控失效最常见的方式。
