# 测试用例 9 列标准格式（权威定义）

> **本文件是全项目测试用例格式的唯一真源。** 其他技能（`qa-api-testing`、`qa-agent-testing`、
> `qa-regression-testing` 等）产出用例时以本定义为准；有冲突以本文件为准。
> 校验工具：`python scripts/validate_testcase_table.py <用例文件>`

## 1. 九列定义

| # | 列名 | 必填 | 填写要求 | 常见错误 |
|---|------|------|---------|---------|
| 1 | 用例编号 | ✅ | `TC_{模块缩写}_{功能缩写}_{三位序号}`，同批内不重号 | 用 `TC_USER_LOGIN_001_NORMAL` 四段式；用 `AGENT-001` |
| 2 | 测试类型 | ✅ | 按所属技能维度填写：功能/安全/异常/性能/契约/兼容性；API 类补安全与契约 | 写"正常用例""异常用例" |
| 3 | 功能模块 | ✅ | 业务模块，必要时用 `模块/子功能` 两级（**子功能并入本列，不单设列**） | 只写"系统""后端" |
| 4 | 测试标题 | ✅ | 动词开头，点明验证点 | 写"测试登录" |
| 5 | 用例级别 | ✅ | P0/P1/P2/P3，占比见 §3 | 全标 P0 |
| 6 | 预置条件 | ✅ | 环境 + 数据 + 权限 + 状态，具体到可复现 | 只写"环境正常" |
| 7 | 测试步骤 | ⚠️ 见 §4 | 协议类必填；实现相关类可留空 | 全留空（丢了可执行性） |
| 8 | 预期结果 | ✅ | 可量化：状态码 / 返回结构 / 数据状态 / 副作用 | 写"正确""正常" |
| 9 | 风险等级 | ✅ | 高（资损/越权/数据错误/安全）/ 中（体验与稳定性）/ 低 | 留空或全标高 |

> **为什么没有"实际结果"列**：那是**执行阶段**的记录字段，由 `qa-execution-observation` 的
> 观察记录承载，不属于设计阶段的用例定义。设计模板塞执行字段会导致执行时被回填污染设计产物。
>
> **为什么没有"子功能"列**：并入「功能模块」用 `模块/子功能` 表示，信息不丢且不增加列宽。
> 9 列是 `validate_testcase_table.py` 与 `测试用例.csv` 的硬约束，不可增减。

## 2. 编号规则

```
TC_{模块缩写}_{功能缩写}_{三位序号}
```

- 模块缩写：业务模块，2-10 位大写字母或数字（`API` / `CART` / `LOGIN` / `ORDER`）
- 功能缩写：功能点，2-10 位（`LOGIN` / `CREATE` / `REFUND`）
- 三位序号：同批内从 `001` 连续递增

示例：
- `TC_API_LOGIN_001` — API 模块 / 登录功能 / 第 1 条
- `TC_CART_ADD_007` — 购物车 / 添加商品 / 第 7 条
- `TC_ORDER_REFUND_003` — 订单 / 退款 / 第 3 条

> **不使用场景后缀**（如 `_NORMAL` / `_JUMP`）。场景类别信息应写进「测试类型」与「测试标题」，
> 塞进 ID 会让 ID 失去稳定的"用例"语义，也破坏与 `SC-{模块缩写}-{序号}` 场景 ID 的对应关系。

## 3. 级别与占比

| 级别 | 含义 | 适用场景 |
|------|------|---------|
| P0 | 关键 | 核心业务流程、主流程验证、资损/安全相关 |
| P1 | 重要 | 主要功能、重要分支流程 |
| P2 | 一般 | 次要功能、异常场景 |
| P3 | 可选 | 边缘场景、极端异常 |

**占比约束**：P0 ≤ 20% / P1 ≤ 40% / P2 ≤ 30% / P3 ≤ 10%

**小规模例外**：用例总数 < 10 条时上述配额在数学上无法成立（20% 不足 1 条）。
此时加 `--no-quota` 跳过校验，并在报告中注明「小规模用例集，按每维至少 1 条覆盖」。
**不要为凑比例编造用例或随意拉高/压低级别。**

## 4. 「测试步骤」该留空还是该填

这是历史上最容易产生分歧的一列，裁决如下：

| 用例类型 | 步骤 | 理由 |
|---------|------|------|
| **协议 / 接口类**（API、gRPC、WebSocket、Webhook、数据库协议） | **必填**，含 method + path + 关键参数 | 步骤由协议契约决定，不依赖实现细节，AI 能准确写出来 |
| **配置 / 规则 / 计算类**（配置项、金额计算、权限矩阵） | **必填** | 同上，规则本身是确定的 |
| **UI / 业务流程类**（页面跳转、交互流程） | **可留空**，标注「由执行人按实际系统补充」 | 同一"登录"功能不同系统实现完全不同，AI 强写必然与实际不符，反而增加修正成本 |

> 历史版本曾一刀切要求"测试步骤留空"，导致 API 类用例丢失了可执行性——
> 而 API 的 method/path 恰恰是**规格的一部分**，不是实现细节。
> 现按类型区分：协议类必填，实现相关类可留空。

## 5. 两种产出形态

### A. 表格形态（默认，批量评审/流转用）

```markdown
| 用例编号 | 测试类型 | 功能模块 | 测试标题 | 用例级别 | 预置条件 | 测试步骤 | 预期结果 | 风险等级 |
|---------|---------|---------|---------|---------|---------|---------|---------|---------|
| TC_API_LOGIN_001 | 功能测试 | 认证/登录 | 正确凭证登录成功 | P0 | 账号 u1 已就绪，接口文档已提供 | POST /api/login，body {"user":"u1","pass":"***"} | 返回 200，响应含 token；调 /api/profile 有效；无堆栈泄露 | 高 |
| TC_API_LOGIN_002 | 安全测试 | 认证/登录 | 伪造 Token 被拒 | P0 | 已知合法 token 与签名算法 | 改 1 个字符后请求 /api/profile | 返回 401；响应不含内部信息与用户数据 | 高 |
```

### B. 展开块（单条用例评审/执行时用）

```markdown
### TC_API_LOGIN_001 — 正确凭证登录成功

- **测试类型**：功能测试
- **功能模块**：认证/登录
- **用例级别**：P0
- **预置条件**：账号 u1 已就绪；接口文档已提供
- **测试步骤**：POST /api/login，body {"user":"u1","pass":"***"}
- **预期结果**：返回 200，响应含 token；调 /api/profile 有效；无堆栈泄露
- **风险等级**：高
```

## 6. 交付前必过校验

```bash
python scripts/validate_testcase_table.py <用例文件>
```

校验 9 列完整、编号唯一且合格式、级别/风险取值合法、P0-P3 占比、
覆盖率措辞带口径、绝对化措辞禁令。**报错先修再交付。**
