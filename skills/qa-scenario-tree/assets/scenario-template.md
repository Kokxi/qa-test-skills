# 场景树与场景描述模板

> 复制下面任一块板填写。四类场景的覆盖清单与构建方法见 [`scenario-types.md`](scenario-types.md)。

## A. 场景树骨架

```text
{功能模块名}
├─ 主路径（SC-{模块}-001 起）
│   ├─ SC-{模块}-001：{正常流程1}
│   └─ SC-{模块}-002：{正常流程2}
├─ 分支路径
│   ├─ SC-{模块}-003：{分支条件1}
│   ├─ SC-{模块}-004：{分支条件2}
│   └─ SC-{模块}-005：{配置组合 / 权限分支}
├─ 异常路径
│   ├─ SC-{模块}-006：{输入异常}
│   ├─ SC-{模块}-007：{依赖异常 + 恢复验证}
│   ├─ SC-{模块}-008：{并发冲突}
│   └─ SC-{模块}-009：{网络异常}
└─ 数据流
    ├─ SC-{模块}-010：{数据创建与关联}
    └─ SC-{模块}-011：{跨模块一致性}
```

> 序号在**整棵树内连续**，不按类别分段 —— 便于按 `SC-{模块}-0xx` 直接查。

## B. 单场景描述块

```markdown
### SC-LOGIN-007 — 支付回调超时后的订单状态

- **路径类型**：异常路径
- **关联需求**：REQ-PAY-003（支付回调处理）
- **前置条件**：
  - 订单处于"支付中"状态已 30 分钟
  - 支付网关回调地址可达但本环境注入 3 秒延迟
- **触发条件**：用户点击"支付"，网关响应超时
- **操作步骤**：
  1. 发起支付，模拟网关 3 秒延迟
  2. 等待超时返回
  3. 查询订单状态
  4. 手动补发一次回调
- **预期结果**：
  - 超时后订单进入"支付中"而非直接判失败
  - 补发回调后订单转为"已支付"，**不产生二次扣款**
  - 30 分钟后仍未收到回调的订单被自动关闭并释放库存
- **数据变化**：
  - 订单：`支付中` → `已支付`
  - 支付单：保持唯一，无重复记录
  - 库存：超时释放后重新扣减，最终净扣减 1
- **风险等级**：高（资损）
```

## 填写要求

| 字段 | 要求 | 常见错误 |
|------|------|---------|
| 场景 ID | `SC-{模块缩写}-{序号}`，三位序号、树内连续 | 用 `TC_` 编场景号（那是用例前缀） |
| 关联需求 | `REQ-{需求模块缩写}-{序号}`，**必填** | 留空（场景树无法回溯到需求） |
| 路径类型 | 四选一：主路径 / 分支路径 / 异常路径 / 数据流 | 写"正常用例""异常用例" |
| 前置条件 | 环境 + 数据 + 状态 + 依赖可控性，具体到可复现 | 只写"环境正常" |
| 触发条件 | 用户操作或系统事件，单句 | 写"各种情况" |
| 操作步骤 | 一步一验证，含具体操作与等待时长 | 写"模拟超时" |
| 预期结果 | 可观测：状态、返回值、数据变化 | 写"正确处理" |
| 数据变化 | 逐个数据对象写清前后状态 | 留空（数据流场景的核心信息） |
| 风险等级 | 高（资损/越权/数据错误）/ 中（体验与稳定性）/ 低 | 全标高 |

## 交付前自检

- [ ] 四类路径都有场景；某一类确实不适用时写"不适用 + 原因"
- [ ] 每个场景 ID 唯一且连续，格式为 `SC-{模块}-{序号}`
- [ ] 每个场景关联到 `REQ-` 需求 ID，无孤儿场景
- [ ] 场景数达到数量要求（×3/×5/×7，按需求数 ×1.5 向下取整的维度已处理小数）
- [ ] 异常路径均验证了**恢复能力**（报错后状态、能否重试、重试有无重复副作用）
- [ ] 数据流场景逐个数据对象写了前后状态
- [ ] 无主路径/异常路径混排
- [ ] 覆盖率已标注口径，无"全覆盖/100%"绝对化表述
