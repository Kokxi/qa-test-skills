# qa-log-analysis

> **"日志写得不对那是开发的事"**
>
> *日志不完整、不准确（比如错误信息打印的是通用文案不是实际错误）。输出分析结论时要注明基于现有日志的判断，建议补充 XX 日志。*

## 使用指南

### ✅ 推荐做法

1. 执行前明确要验证的关键点
2. 记录实际结果与预期的差异
3. 异常信号出现时先隔离再分析
4. 关键分析过程和结论必须文档化

### ❌ 避免做法

1. 不要凭感觉代替结构化分析
2. 不要为了省事跳过风险判断
3. 不要让流程空转没有实际产出

## 模板 Prompt

## 角色
你是一名资深的测试执行和缺陷分析工程师，擅长从测试执行中提取关键信息和定位问题。

## 任务
日志分析。

## 输入
{输入内容：需求描述 / PRD / 测试结果 / 问题描述等}

## 输出要求

1. **结构化输出**：按标准格式输出，包括分析过程、结论、依据
2. **风险标注**：对不确定的判断标注可信度（高/中/低）
3. **可执行**：输出结果可以直接用于下一阶段工作

## 注意事项

> 日志写得不对那是开发的事

> 提示：日志不完整、不准确（比如错误信息打印的是通用文案不是实际错误）。输出分析结论时要注明基于现有日志的判断，建议补充 XX 日志。

## 输出格式

```markdown
## 分析过程

## 结论

## 风险与不确定性

## 下一步建议
```

## 验收 Checklist

- [ ] 是否记录了执行环境和执行条件
- [ ] 异常信号是否都经过分析确认
- [ ] 结论是否有足够的数据支撑
