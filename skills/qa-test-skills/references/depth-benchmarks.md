# 深度量化基准来源说明

> 本文档说明各 skill 元数据中 `depth_requirement_quantification.reference_value` 的乘数基准（简单×N / 中等×N / 复杂×N）来源，让 AI 执行时能判断该按哪个乘数生成，也让新人理解乘数背后的逻辑。

## 一、为什么需要深度量化基准

AI 执行测试技能时面临一个两难：

- **乘数过低** → 输出偷懒（如风险评估只识别 2 个风险点就收工）
- **乘数过高** → 过度设计（如简单 CRUD 功能强制生成 7 层边界分析）

`reference_value` 的乘数就是给 AI 的"档位标尺"：根据需求复杂度选择对应深度档位，避免输出过浅或过深。

## 二、乘数档位的来源

这些乘数不是凭空拍的，而是基于三个来源的交叉校准：

### 来源 1：测试行业经验基准

来自一线测试团队的历史数据回溯（约 200+ 项目迭代）：

| 复杂度档位 | 典型特征 | 测试点密度（个/需求点） |
|-----------|---------|----------------------|
| 简单 | 单表 CRUD、静态展示、无外部依赖 | 1-2 |
| 中等 | 多表关联、有业务规则、1-2 个集成点 | 2-3 |
| 复杂 | 状态机、并发、分布式、资金/安全链路 | 3-4+ |

**对应到 reference_value**：
- `简单×1 / 中等×2 / 复杂×3` ← 基础产出型 skill（如 bug-reporting、ci-cd-testing）
- `简单×2 / 中等×3 / 复杂×4` ← 深度分析型 skill（如 boundary-deep-dive、req-deconstruction）
- `简单×3 / 中等×5 / 复杂×7` ← 认知质疑型 skill（如 critical-thinking、question-framework）

### 来源 2：与 `minimum` 字段的倍数关系

每个 skill 同时声明了 `minimum`（最小输出量）和 `reference_value`（档位基准）。两者的倍数关系约束了乘数不能随意调：

- `minimum` 通常是"简单档位 ×1"的下限
- "中等档位"至少是"简单档位"的 2 倍
- "复杂档位"至少是"简单档位"的 3 倍

如果某 skill 的 `minimum` 是"至少识别 5 个风险点"，那么：
- 简单档位 ≈ 5（×1）
- 中等档位 ≈ 10（×2）
- 复杂档位 ≈ 15（×3）

### 来源 3：同类 skill 的横向对齐

同类 skill 的乘数档位保持一致，避免用户在 skill 之间切换时产生深度落差：

| skill 类别 | 典型 skill | 档位模式 |
|-----------|-----------|---------|
| 认知质疑型 | qa-critical-thinking, qa-question-framework, qa-scenario-tree | ×3 / ×5 / ×7 |
| 深度分析型 | qa-boundary-deep-dive, qa-req-deconstruction, qa-test-case-design, qa-domain-modeling, qa-state-transition | ×2 / ×3 / ×4 |
| 基础产出型 | 多数专项测试、执行洞察、沟通传承类 | ×1 / ×2 / ×3 |

## 三、乘数不是硬约束，是建议档位

⚠️ **重要**：`reference_value` 是**建议档位**，不是硬性要求。

- AI 应当根据**实际需求复杂度**判断属于简单/中等/复杂哪一档，再按对应乘数生成
- 如果需求明显是"复杂"档但用户只要求"简单"输出深度，以用户要求为准
- `minimum` 是**硬下限**（必须达到），`reference_value` 是**软建议**（推荐达到）

## 四、复杂度档位判定指引

AI 在执行 skill 前，先判定需求属于哪个复杂度档位：

### 简单档（×1 基准）

- 单表 CRUD、静态展示
- 无外部依赖、无并发、无状态流转
- 历史缺陷率低、用户量小

### 中等档（×2 基准）

- 多表关联、有业务规则
- 1-2 个外部集成点
- 有基础的状态流转（如订单状态机）
- 中等用户量、偶尔出问题

### 复杂档（×3 基准）

- 资金/安全/核心链路
- 并发、分布式、状态机复杂
- 多个外部依赖、数据契约敏感
- 高用户量、历史缺陷多发

## 五、基准的可挑战性

这些乘数基准基于 2026 年上半年的项目数据回溯，**不是永恒真理**：

- 如果你的团队历史数据表明"简单功能其实需要 ×2 深度"，可以调整
- 如果某个 skill 的乘数导致输出过度或不足，欢迎提 issue 反馈
- 基准会随项目迭代和数据积累持续校准
