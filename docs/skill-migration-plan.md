# 剩余 47 个技能内容层优化计划

> 样板已完成：`qa-api-testing`、`qa-agent-testing`（见 [`skill-content-layout.md`](skill-content-layout.md)）。
> 本计划基于全量测量（`scripts/` 下 survey 脚本实测），非估算。

## 一、现状测量结果

| 指标 | 实测值 |
|------|--------|
| 待优化技能 | 47 个 |
| SKILL.md 合计 | **11052 行 / 约 75k token**（Activation 阶段每次触发都付） |
| 零 references（需从零拆） | **38 个** |
| 缺加载时机地图 | **46 / 47** |
| 缺 assets（产出模板） | **47 / 47** |
| SKILL.md 行数区间 | 96 – 333 行 |

**剔除误报**：初测有 4 个技能报"编号格式不一致"，核实后 `ST-`/`COMBO-` 是 standards.md 已定义的
合规前缀，`AUTH`/`API`/`ORDER` 是样例中的模块缩写（`TC_{模块缩写}` 本就允许）。这些不算缺陷。

**真缺陷只有一处**：`qa-state-transition` 的 15 个 ID 形如 `ST-合法-001`，
ID 里塞了中文，违反 `{模块缩写}` 的 ASCII 假设，排序与 grep 都会别扭。

## 二、关键决策：按产出物分批，不按体积分批

拆分边界由**这个技能产出什么**决定，不由它多长决定：

- 产 9 列用例表的技能 → 共享同一份 `assets/case-template.md`，**边际收益最高**（第 1 批）
- 产分析表/评审报告的 → 模板不同但结构相似（第 2 批）
- 产报告/计划的管理类 → 模板化程度低，收益主要来自下沉方法论详图（第 6 批）
- 入口工作流引用全部子技能 → **放最后**，否则前面每批都在改它的依赖

## 三、分级改造（方案 B）

**不搞 47 个技能平权改造。** 用依赖图入度 × 工作流步骤 × 产出形态加权选高价值技能，
其余做轻量合规。理由：方法论类技能的内容很多每次都要读，硬拆只增加跳转成本，
不省上下文还损可读性。

## 三·补、跨全项目的系统性污染（已修）

调查中发现一个所有现有检查都看不见的缺陷：

**46/49 个技能的 `output_format.structure` 开头被粘上了同一段样板**：

```json
["测试用例表格：固定 9 列（用例编号|测试类型|...|风险等级）",
 "用例级别：P0≤20%（核心流程）/ P1≤40%...",
 "覆盖率：标注口径（基于现有需求/输入文档）...", 
 {"该技能真实产出字段": "..."}]
```

其中 **12 个技能根本不产测试用例**——它们的真实产出是缺陷报告、复盘报告、质量看板、
发布方案、左移计划、团队赋能方案。样板让 AI 以为要输出用例表，是实打实的错误指令。

| 分组 | 数量 | 处理 |
|------|------|------|
| A 真产用例表，样板合理 | 34 | 保留 |
| B 真产表但已自行改正 | 3 | — |
| **C 虚假声明** | **12** | **已删除样板行** |

已加 `integrity_check` 检查项 13 防回归（只判"零表格却声明"，不判"正文未内嵌样例"——
`output_format` 是产出契约，声明格式而不贴样例是合法的）。

## 四、第 0 批：先建尺子，再动针

**这一批不做内容，只加检查**。理由：没有尺子，47 个技能的改造就是"我觉得改好了"。

新增 3 项检查到 `check_spec_compliance.py` / `integrity_check.py`：

1. **加载时机地图存在性** —— SKILL.md 缺 `加载时机`/`什么时候读` 章节则告警
2. **assets 目录存在性** —— 产出型技能应至少有一个模板文件（warning 级）
3. **ID 不含中文** —— 扫 `PREFIX-中文-序号` 形态（当前命中 `qa-state-transition` 15 处）

### 棘轮机制（关键设计问题）

加了检查后门禁会立刻变红（46/47 不合规）。这不是"引入新问题"，而是**暴露存量债**，
但会让 CI 无法区分"新引入的"和"本来就有"。

**方案**：加 `scripts/layout_baseline.json` 记录当前存量，
检查只对**超出基线的新增违规**失败。每完成一批，从基线里移除对应技能。

```json
{
  "no-load-map": ["qa-xxx", "..."],
  "no-assets": ["qa-yyy", "..."],
  "id-has-cjk": ["qa-state-transition"]
}
```

这样门禁从第一天起就是绿的，且**每批改造完基线自动收缩**——进度可见，回归可拦。
替代方案（直接让门禁红）会让这次改造没法用 CI 卡住，不采纳。

## 五、每批的执行流程（固定）

> 深层组走完整 9 步；浅层组只走 1/2/3/6/8/9 步。

1. 读全该批每个技能 + 已有 references
2. 决定拆分边界：什么留正文（决策逻辑）、什么进 references（按需）、什么进 assets（产出模板）
3. 写加载时机地图 —— **不写地图就不算完成拆分**
4. 写 `assets/` 产出模板（含"填写要求 + 常见错误"表）
5. 更新 `metadata.references`（新增的 assets 也要登记）
6. 清理跨边界重复（正文清单 vs references 详图，二选一）
7. 顺带修该技能的实际缺陷（编号矛盾、配额不可取整、绝对化措辞、声明数字与实际不符）
8. 跑 `python scripts/run_qa.py all` + 官方 `skills-ref validate`
9. 更新 `layout_baseline.json`，本批单独提交

## 六、工作量与节奏

- 深层组 9 个 + 浅层组约 33 个，按每批 3-5 个计，约 **10-12 轮**
- 单个技能典型动作：读 → 定边界 → 写 1 个 SKILL.md + 1-3 个 references + 1 个 assets
  → 改 metadata → 跑门禁。**约 4-6 个技能/轮**，预计 8-10 轮完成
- 建议每批一个 commit，便于按批回滚；第 1 批完成后先停下确认效果，再继续

## 七、验收标准

全部完成后应达成：

- 47 个技能全部有 `加载时机地图`
- 用例产出型技能全部有 `assets/case-template.md`（共享同一 9 列格式）
- `layout_baseline.json` 清空（可删除）
- SKILL.md 合计行数下降约 40%，**决策信息零丢失**
- `python scripts/run_qa.py all` + 官方 `skills-ref validate` 全绿
- 顺带修掉的实质缺陷：`qa-state-transition` 的 15 个中文 ID、`qa-mobile-testing` 的
  清单重复与配额不可取整、`qa-combination-strategy` 的 description 绝对化措辞
