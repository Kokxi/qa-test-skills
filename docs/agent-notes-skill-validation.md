# Skill 项目质量验证与优化经验笔记（AI Agent 复用版）

> 本文档由 qa-team-skills v1.5.0 分支的实战复盘提炼，供 AI Agent 在其他 skill 项目复用。结构化、带命令、带判定逻辑、带诊断决策树——拿到能直接照做。

## 0. 适用判定

```
IF 项目形态 == 纯 Prompt AI 技能包（无 HTTP server，靠 LLM 按 prompt 执行）
AND 项目含 prompts/ 目录 + SKILL.md + 多个指令（/qa-xxx）
THEN 适用本经验文档
ELSE 需先适配架构（本文档的脚本金字塔思路通用，但具体实现要改）
```

## 1. 核心方法论：验证金字塔

**关键认知**：多数 skill 项目只有 demo 没有评测。验证不止于"跑几个 demo 看输出像不像"——要建分层脚本金字塔，每层过滤不同问题。

| 层 | 查什么 | 工具形态 | 发现什么 |
|----|--------|---------|---------|
| 1 静态结构 | 文件齐全/字段完整/版本一致/无硬编码行业词 | bash 脚本 + forbidden.txt | 缺失、不一致、BOM 等字节级 bug |
| 2 动态契约 | prompt 定义与 eval 期望是否一致 | bash/python 静态断言 | prompt 定义错误（如维度数写错） |
| 3 行为模拟 | 复杂模块（记忆/状态机）规则实现是否偏离规范 | python 模拟器复刻规则 | 规则实现 bug（如版本清理丢数据） |
| 4 长期压测 | 多轮迭代后性能退化/重复堆积 | python 模拟 10 轮 | 长期使用才暴露的缺陷 |
| 5 真·LLM 端到端 | 模型实际产出满足断言否 | python + LLM API + LLM-as-judge | **内容质量缺陷（结构断言查不出）** |
| 6 人工双盲 | 维度分析对不对/用例合不合理 | 流程文档+评分表 | 内容真有用否 |

**Agent 复用要点**：
- 层 1-4 是免费秒级脚本，必建
- 层 5 是关键——前 4 层查不出"模型真遵守否"，必接 LLM API
- 层 6 是人工流程，发版前执行

## 2. 各层脚本的最小实现规范

### 层 1：静态结构校验（validate.sh）

**必查项**（按需调整）：
- 必需文件齐全（SKILL.md、各指令 prompt.md、模板、docs、examples）
- 每个 prompt 含「防注入声明」「输出前自检」章节
- VERSION 文件与 SKILL.md frontmatter 版本一致
- 无硬编码行业词（forbidden.txt 定义）
- 无旧目录残留

**字节级 bug 检查**：脚本开头查 UTF-8 BOM（`head -c 3 file | od -An -tx1` 含 `ef bb bf`），BOM 会污染 shebang。

### 层 2：契约断言（run-evals.sh）

把 `evals/functional-eval.json` 的 assertion 翻译成对 prompt 文件的静态检查：
- 维度数：`grep -cE '^\| [0-9]+ \|' prompt.md` ≥ 期望值
- 必含字段：`grep -qE '设计方法.*必填' prompt.md`
- schema 一致性：对比各 prompt 的章节顺序

**产出**：通过数/总数 + 失败明细 + 归档报告到 `evals/history/`。

### 层 3：行为模拟（test-memory-e2e.sh）

若项目含记忆/状态模块，用 python 模拟器复刻 `README.md` 定义的规则，在临时目录跑完整生命周期：
- 写入 → 合并去重 → 重新编号 → 版本清理 → 历史加载
- 每步断言符合规范

**关键**：测试完自动清理临时目录，不污染真实数据。

### 层 4：长期压测（test-memory-stress.sh）

模拟 10 轮迭代，断言：
- summary/索引文件体积线性增长（比值 ≤ 5x，非爆炸）
- 读取延迟不退化（比值 ≤ 3x）
- 去重生效（无重复堆积）
- 版本清理生效（保留最近 N 个）

**这一层常挖真缺陷**——单轮正确 ≠ 长期稳定。

### 层 5：真·LLM 端到端（run_llm_eval.py）★关键

**架构**：
```
读 evals/functional-eval.json 每条 eval
  → 解析 prompt 开头的 /qa-xxx 指令
  → 加载 prompts/xxx/prompt.md 作为 system prompt
  → prompt 剩余部分作为 user message
  → 调 worker 模型生成产出
  → 对每条 assertion 调 judge 模型判定 pass/fail
  → 归档报告到 evals/history/
```

**judge system prompt 模板**（强制结构化输出）：
```
你是一个严格的测试质量评审员。你会收到一份 AI 生成的产出和一条断言。
判断该产出是否满足这条断言。
只输出一行 JSON：{"pass": true, "reason": "简要说明"}
不要输出任何其他内容。
```

**模型选型决策树**：
```
IF 项目预算 == 0
  THEN 用免费模型（如 cohere/north-mini-code:free）做基线
       注意：免费模型在长 system prompt 下产出可能为空，能力上限低
ELSE 用 deepseek-chat（非 reasoning、产出完整、¥0.001/k token）
     一轮全量评测约 53k token = 5 分钱
FI

IF 模型 == reasoning 模型（kimi-for-coding/glm-5.2）
  THEN max_tokens 需 ≥ 16384（reasoning_content 占大量 token）
       temperature = 1（reasoning 模型常限定）
       兜底：content 为空时回退用 reasoning 尾部
ELSE max_tokens = 8192, temperature = 0.3（评测要稳定）
FI
```

**API key 安全纪律**：
- 仅从环境变量读（`os.environ.get("DS_KEY")`）
- 绝不写入脚本或归档报告
- 每次 commit 前 `git diff --cached | grep -E "真key前缀"` 检查
- 示例占位符 `sk-...` 不算泄露

**requires_e2e 标注**：
若某条 eval 的断言依赖文件 I/O（如"读取 standards.json"），纯 LLM 评测器看不到文件内容，跑不过不是 prompt 缺陷。标注 `requires_e2e: true` 从基线排除，改用层 3 的端到端模拟器验证。**不得为提分改评测器注入文件数据自欺**。

## 3. 缺陷诊断决策树

当 LLM 评测准确率低，按此树诊断：

```
准确率低
├─ eval 全部 error（无产出）
│   ├─ HTTP 403/429 → API 配额/限流，换模型或等重置
│   ├─ content 为空 + finish=length → max_tokens 太小，调到 8192+
│   └→ content 为空 + finish=stop → 模型能力上限，换更强模型
│
├─ eval 部分通过，失败项分散
│   ├─ 失败原因"漏维度" → prompt 加硬约束：逐编号输出+末尾覆盖统计+缺项即校验失败
│   ├─ 失败原因"误判XX" → prompt 指令模糊，明确判定标准（含X即视为Y）
│   ├─ 失败原因"只承诺不输出" → prompt 加硬约束：必须直接输出内容，询问确认不得替代
│   └→ 失败原因"维度命名不对齐" → 改 eval assertion 描述，硬编码具体维度名
│
└─ eval 部分通过，失败项集中在某指令
    ├─ 该指令 prompt 定义有缺 → 修 prompt
    └→ 该指令 eval assertion 描述有误 → 修 eval
```

## 4. 常见缺陷模式与修复模板

### 模式 A：漏维度/漏类型

**症状**：prompt 定义了 N 个维度/类型，模型实际输出 < N。

**根因**：模型在复杂输出时按训练分布惯性遗漏，尤其是后加的或非典型的维度。

**修复模板**：
```
> ⚠️ **N 个维度全必输出硬约束**：必须按编号 1-N 逐条输出，未发现问题的也要输出占位行。
> 不适用的也要输出标注"不适用+原因"的占位项，而非省略。
> 末尾的"维度覆盖统计"必须确认 N/N 全覆盖，缺一项即格式校验失败。
```

**实测效果**：prd-001 从 0/5 → 5/5，agent-001 从 2/5 → 5/5。

### 模式 B：误判"信息不足"拒绝执行

**症状**：eval 提供的信息其实充分，模型却说"信息不足无法执行"。

**根因**：prompt 写了"信息不足时拒绝"，但没定义"信息充分"标准，模型按最保守路线误判。

**修复模板**：
```
> ⚠️ **"信息充分"判定标准（不可误判）**：
> 含 X + Y + Z 三项即视为信息充分，必须执行。
> 不得因可选辅助信息（环境/日志/截图）缺失而误判为信息不足。
> 仅当三项中有任一缺失或极度模糊时才可判定信息不足。
```

**实测效果**：bug-001 从 0/5 → 5/5。

### 模式 C：只承诺不输出

**症状**：模型回"我将生成报告"但没真生成表格。

**根因**：prompt 没硬约束"必须直接输出"。

**修复模板**：
```
> ⚠️ **必须直接输出，不得只承诺生成**：
> 必须在本次响应中直接输出完整内容，不得只输出"我将生成"等承诺性表述。
> 询问确认不得替代直接输出——用户请求即默示授权，询问只能在输出末尾的"是否补充"环节。
> 若数据不足，先输出已有数据的分析，再标注缺什么。
```

**实测效果**：team-001 从 1/4 → 4/4。

### 模式 D：误标"不适用"

**症状**：被测对象含某能力，模型却把对应测试维度标成"不适用"。

**根因**：prompt 写"仅在涉X时生成"，但没明确判定规则，模型误判。

**修复模板**：
```
> ⚠️ **适用判定规则**：
> 描述中含"X/关键词1/关键词2"等词 → 标注为适用，必须生成
> 描述中明确无该能力（如"仅工具调用无X"）→ 标注"不适用"+原因
> 不得在涉及时误标"不适用"——这是常见错误
```

**实测效果**：agent-001 从 3/5 → 5/5。

### 模式 E：长期使用丢数据

**症状**：单轮正确，多轮后版本清理删旧版本，早期唯一数据丢失。

**根因**：合并逻辑只读磁盘现存文件，清理删了旧版本，这些版本里的唯一数据就没了。

**修复**：改为"以现有 latest/合并文件为基线再并入新版本"，清理只删版本文件不丢基线里的合并数据。

**实测效果**：压测 6/6 全过，无数据丢失。

## 5. 执行顺序（Agent 照做）

```
STEP 1: 探查项目结构
  - ls prompts/ SKILL.md VERSION evals/ docs/
  - 确认项目形态（纯 Prompt / 有 server）

STEP 2: 建/跑层 1 静态校验
  - 若无 validate.sh → 建之（参考层 1 规范）
  - 若有 → bash ci/validate.sh，修所有报错

STEP 3: 建/跑层 2 契约断言
  - 若无 run-evals.sh → 建之
  - 若有 → bash ci/run-evals.sh，修所有契约不符

STEP 4: 若项目含记忆/状态模块 → 建/跑层 3+4
  - test-memory-e2e.sh + test-memory-stress.sh

STEP 5: 接 LLM API 建层 5
  - 选模型（按模型选型决策树）
  - 写 run_llm_eval.py（按层 5 架构）
  - 先 --smoke 跑单条验证管线
  - 全量跑，记录基线准确率

STEP 6: 按缺陷诊断决策树修 prompt
  - 准确率 < 70% → 按模式 A-E 修
  - 每修一处 → 重跑层 5 验证提升
  - 迭代直到准确率 ≥ 90% 或剩模型能力上限的随机波动

STEP 7: 标注 requires_e2e
  - 跑不过若是评测器架构限制（依赖文件 I/O）→ 标注排除
  - 不得为提分改评测器自欺

STEP 8: 归档 + 报告
  - evals/history/ 存每轮报告
  - 写人可读总结（基线→修复→最终准确率）
```

## 6. 避坑清单

| 坑 | 表现 | 解法 |
|----|------|------|
| UTF-8 BOM | 脚本直接执行报 shebang 错误 | `head -c 3` 查 BOM，去除 |
| Windows CRLF | 字符串比较失败（值相同却判不等） | 统一 `tr -d '\r\n'` |
| python3 占位符 | Windows Store 的 python3 调用即挂 | 回退用 `python` |
| reasoning 模型 max_tokens 太小 | content 为空，finish=length | 调到 16384+ |
| API key 泄露 | key 写进脚本或归档报告 | 仅环境变量 + commit 前检查 |
| 为提分改评测器 | 注入文件数据让分数好看 | 诚实标注 requires_e2e |
| 单轮正确 | 以为长期也正确 | 必跑长期压测 |
