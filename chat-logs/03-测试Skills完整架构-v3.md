# 软件测试 Skills 完整架构 v3

## 设计前提

- **目标**：把资深测试的"隐性知识"变成可加载的技能，降低 Junior + AI 的门槛
- **覆盖范围**：不仅仅是测试技术，而是资深测试完整的能力光谱
- **每个技能的通用结构**：思维框架 → 提示词模式 → 验收 checkist → 常见翻车点

---

## 专家知识的七个维度

```
┌─────────────────────────────────────────────────────────────────────────┐
│  1. 认知与思维          — 专家怎么想问题（思维模式、框架、直觉）           │
│  2. 需求到模型          — 专家怎么把模糊需求变成结构化测试模型              │
│  3. 深度设计            — 专家做测试设计的套路（边界、组合、状态、启发式）   │
│  4. AI 协作             — 专家怎么用 AI（上下文构建、提问、评审、补盲）     │
│  5. 执行洞察            — 专家执行时在看什么（日志、现象、Bug 根因）        │
│  6. 策略架构            — 专家的全局视角（策略、风险、度量、可测试性）       │
│  7. 沟通传承            — 专家的影响力（怎么让人听你的、怎么赋能团队）       │
└─────────────────────────────────────────────────────────────────────────┘
```

### 簇 1：认知与思维（Testing Cognition）

> 这些是"内功"，不直接产出用例，但决定了其他所有技能的上限。

#### 1.1 `qa-critical-thinking` — 测试批判性思维

| 内容 | 说明 |
|------|------|
| **解决的问题** | Junior 看到需求只会跑主流程，不会质疑 |
| **专家经验** | 对每个"应该"都问"如果不呢？"；对每个"正常"都问"异常呢？"；对每个"确定"都问"假设呢？" |
| **核心框架** | 5W1H 质疑法、逆向思维、假设挖掘、always ask "那又怎样" |
| **AI 怎么问** | 给 AI 一个功能描述，要求按"质疑框架"输出所有可能的假设和反例 |
| **验收 checkist** | 是否覆盖了：显性假设 / 隐含假设 / 边界情况 / 故障模式 / 用户误操作 |

#### 1.2 `qa-risk-intuition` — 风险直觉

| 内容 | 说明 |
|------|------|
| **解决的问题** | Junior 对风险不敏感，看不出"什么会出事" |
| **专家经验** | 有经验的测试看到某些变更描述、代码改动、业务场景，会本能地警觉。这不是玄学，是可以结构化的信号模型 |
| **核心框架** | 风险信号雷达：变更类型信号（重写/重构/替换第三方）→ 业务影响信号（资金/安全/核心链路）→ 数据风险信号（迁移/映射/格式转换）→ 集成风险信号（依赖方变更/新接入方） |
| **AI 怎么问** | "这是一个 [变更描述]，请按风险信号雷达分析各维度风险等级，并建议测试深度" |
| **验收 checkist** | 是否识别出了"看起来简单但实际风险高"的区域 |

#### 1.3 `qa-question-framework` — 提问框架

| 内容 | 说明 |
|------|------|
| **解决的问题** | Junior 不知道该问什么问题来获取信息，只能被动接受需求 |
| **专家经验** | 专家不是"知道答案"，而是"知道该问什么"。对需求文档、代码变更、Bug 报告有一套固定的提问链 |
| **核心框架** | 场景化提问模板：拿到需求时问什么、评审用例时问什么、报 Bug 前问自己什么 |
| **AI 怎么问** | "我有一个 [场景]，但缺少以下信息，请生成我需要追问的问题清单" |
| **验收 checkist** | 提问是否覆盖了：信息缺口 / 假设验证 / 边界确认 / 异常处理 / 非功能需求 |

#### 3.4 `qa-heuristic-checklist` — 启发式检查清单

| 内容 | 说明 |
|------|------|
| **解决的问题** | Junior 面对一个未知类型的功能不知道怎么入手 |
| **专家经验** | 对不同类型的功能（列表类/表单类/支付类/导入导出类/审批类/消息通知类），资深测试脑子里有一份"这类功能通常要测什么"的 mental checklist |
| **核心框架** | 功能类型 × 测试维度的矩阵。比如：**支付类**一定要测：重复支付、部分退款、金额精度、超时回调、幂等、并发扣款。**导入类**一定要测：格式兼容、编码、字段映射、部分成功、大文件、空文件、数据校验、进度反馈 |
| **AI 怎么问** | "这是一个 [功能类型] 的功能，描述如下：[描述]。请基于该类型的常见陷阱输出测试要点" |
| **验收 checkist** | 是否覆盖了该类型功能已知的 Top N 类线上故障模式 |

### 簇 4：AI 协作（AI Collaboration）

> 这是整套 Skills 的差异化价值——不是教人怎么用 AI，而是教人怎么让 AI 产出专家级的输出。

#### 4.1 `qa-ai-context-engineering` — AI 上下文工程

| 内容 | 说明 |
|------|------|
| **解决的问题** | Junior 直接问 AI "生成测试用例"，输出泛泛 |
| **专家经验** | 专家知道给 AI 什么信息它才能产出好结果。核心不是"给更多信息"，而是"给对的信息结构" |
| **核心框架** | 上下文金字塔：顶层（业务目标 & 用户角色）→ 中层（功能描述 & 约束条件）→ 底层（技术细节 & 历史缺陷）→ 边界层（输出格式 & 质量要求）。每一层给到什么程度取决于难度 |
| **AI 怎么问** | 不直接问"生成用例"，而是先组装上下文包：业务背景 + 技术架构 + 测试关注点 + 输出要求。格式化为结构化的上下文 |
| **验收 checkist** | 上下文是否包含：业务目标 / 功能边界 / 已知风险 / 测试目标 / 输出规范 / 负面例子 |

#### 4.2 `qa-ai-prompt-strategy` — AI 提示词策略

| 内容 | 说明 |
|------|------|
| **解决的问题** | Junior 只会一种问法，无法引导 AI 深度思考 |
| **专家经验** | 不同的测试阶段/目标，需要用不同的提示词模式去引导 AI。专家脑子里有一张"什么场景用什么问法"的映射表 |
| **核心框架** | 提示词模式库：**结构化输出模式**（"按 XX 框架输出"）、**角色扮演模式**（"你是这个功能的资深用户"）、**分步引导模式**（"先分析边界，再生成用例，最后标注风险"）、**反向质疑模式**（"以上输出中，你觉得哪些场景最可能被你遗漏？"）、**多视角模式**（"从用户/开发/运维三个角度分别分析"）、**对抗模式**（"我对你的输出有质疑：XX场景下你考虑过吗"） |
| **AI 怎么问** | 根据目标选择合适的问法模板，注入上下文 |
| **验收 checkist** | 提示词是否包含：角色 / 上下文 / 框架 / 输出格式 / 约束条件 / 示例 |

#### 4.3 `qa-ai-output-critique` — AI 输出评判

| 内容 | 说明 |
|------|------|
| **解决的问题** | AI 输出看起来都对，但 Junior 看不出哪里不够 |
| **专家经验** | 专家能一眼看出 AI 输出是"合格"还是"优秀"，以及哪里还可以深挖 |
| **核心框架** | 六维评审（同 v2）+ 假设挖掘（"AI 在这个输出里做了哪些假设？这些假设合理吗？"）+ 追问决策（不满意时，是调上下文、换提示词、还是局部追问？） |
| **AI 怎么问** | "评价以上输出的完整性和深度，识别你的假设，建议从哪个方向迭代" |
| **验收 checkist** | 是否识别了 AI 的隐含假设 / 是否评估了覆盖完整性 / 是否有明确的迭代方向 |

#### 4.4 `qa-ai-blindspot-compensation` — AI 盲区补偿

| 内容 | 说明 |
|------|------|
| **解决的问题** | AI 有系统性的盲区——它不太会思考"时序"、"并发"、"资源竞争"、"状态累积"等问题 |
| **专家经验** | 专家知道 AI 在哪些维度上天生弱，主动对这些维度做补盲 |
| **核心框架** | AI 已知盲区：时序依赖（操作顺序变更）、并发冲突（多人同时操作）、资源竞争（内存/连接/线程耗尽）、状态累积（长时间运行后的状态漂移）、数据一致性（分布式场景）、第三方集成（Mock 响应和真实行为差异）。针对每个盲区有专门的追问模板 |
| **AI 怎么问** | "对于以上场景，请额外检查以下 AI 易漏维度：时序/并发/资源耗尽/状态累积/数据一致性" |
| **验收 checkist** | 是否对 AI 盲区维度做了专项检查 |

### 簇 5：执行洞察（Execution Insight）

> 专家的"眼睛"和 Junior 不一样——同样在执行，专家看到了更多信息。

#### 5.1 `qa-execution-observation` — 执行观察力

| 内容 | 说明 |
|------|------|
| **解决的问题** | Junior 执行测试时只关注"过没过"，看不到"异常信号" |
| **专家经验** | 专家看返回 body、看响应时间、看日志、看控制台报错、看数据库状态、看网络请求——所有这些都是信号 |
| **核心框架** | 执行时的六路信号：功能结果（对/错）、性能信号（慢了多少）、日志信号（有没有异常/warning）、数据信号（写库对不对）、前端信号（报错/白屏/卡顿）、依赖信号（第三方返回异常） |
| **AI 怎么问** | 这个技能偏向人的观察力训练，AI 辅助有限。但可以让 AI 生成"执行时应该关注什么"的 checkist |
| **验收 checkist** | 执行时是否观察了：返回结果 / 响应时间 / 日志 / 数据状态 / 前端表现 / 依赖表现 |

#### 5.2 `qa-bug-root-cause-analysis` — Bug 根因分析

| 内容 | 说明 |
|------|------|
| **解决的问题** | Junior 只能描述现象，专家能倒推出根因方向 |
| **专家经验** | 看到某个错误代码、日志、现象，能快速缩小根因范围。这不是魔法，是可学习的"症状→根因"映射模式 |
| **核心框架** | 症状分类（返回错误 / 数据不对 / 性能退化 / 没反应 / 偶发）→ 各症状对应常见根因模式 → 验证方法 |
| **AI 怎么问** | "症状：[描述]，请分析可能的根因方向，按概率排序，给出验证建议" |
| **验收 checkist** | 根因分析是否覆盖了：代码层 / 数据层 / 环境层 / 依赖层 / 配置层 |

#### 5.3 `qa-bug-reporting` — Bug 报告艺术

| 内容 | 说明 |
|------|------|
| **解决的问题** | Junior 提的 Bug 开发看不懂、不想修、修不对 |
| **专家经验** | 好的 Bug 报告不只是"描述问题"，而是帮开发缩小排查范围、提供足够信息让开发一次修复 |
| **核心框架** | Bug 报告黄金结构：标题（是什么+在哪+什么条件下）→ 前置条件 → 复现步骤（精确到每一步）→ 预期 vs 实际 → 附件的门道（怎么截图、怎么抓包、怎么录屏）→ 根因推测（如果有）→ 影响范围评估 |
| **AI 怎么问** | "以下是 Bug 现象描述，请帮我优化为标准的 Bug 报告格式，补充可能缺失的信息" |
| **验收 checkist** | 报告是否包含：精确标题 / 复现步骤 / 预期vs实际 / 附件 / 环境信息 / 影响评估 |

### 簇 6：策略架构（Strategy & Architecture）

> 从"测好一个功能"到"管好一个项目的质量"。

#### 6.1 `qa-test-strategy-design` — 测试策略制定

| 内容 | 说明 |
|------|------|
| **解决的问题** | Junior 拿到项目不知道该怎么分配测试资源、选择测试手段 |
| **专家经验** | 能根据项目特征（工期/复杂度/团队/风险）制定分层测试策略：哪些自动化、哪些手动、哪些深度测、哪些冒烟过就行 |
| **核心框架** | 测试策略六要素：项目背景评估（阶段/团队/技术栈）→ 风险分析（识别高风险区域）→ 分层策略（单元/集成/E2E的比例）→ 手段选择（自动/手动/工具辅助）→ 资源分配（人力/时间/环境）→ 准入准出标准 |
| **AI 怎么问** | "以下是项目信息：[描述]，请推荐测试策略方案，包括分层策略、自动化 vs 手动的分界线、风险优先级" |
| **验收 checkist** | 策略是否覆盖了：自动化策略 / 手动测试聚焦点 / 风险应对 / 资源分配 / 准入门槛 |

#### 6.2 `qa-release-risk-governance` — 发布风险管理

| 内容 | 说明 |
|------|------|
| **解决的问题** | Junior 只关注"测没测完"，不关注"能不能发" |
| **专家经验** | 发布决策不仅仅是"Bug 都修完了没"，而是综合判断：变更影响面、灰度策略、回滚能力、线上验证方案、监控告警完备性 |
| **核心框架** | 发布风险评估矩阵：变更特征分析（改动范围/风险等级）→ 灰度策略设计（按用户/流量/地域逐步放量）→ 回滚方案（回滚条件、回滚步骤、影响评估）→ 线上验收方案（验证什么、谁验证、验证多久）→ 监控告警检查（业务监控是否覆盖、告警阈值是否合理） |
| **AI 怎么问** | "这是一个[版本描述]，请帮我做发布风险评估，包括灰度策略建议和线上验证方案" |
| **验收 checkist** | 是否定义了明确的回滚条件 / 灰度方案是否分阶段 / 线上验证指标是否量化 / 监控告警是否就绪 |

#### 6.3 `qa-quality-metrics` — 质量度量体系

| 内容 | 说明 |
|------|------|
| **解决的问题** | 不知道怎么量化质量，说不清楚"质量到底好不好" |
| **专家经验** | 质量不是感觉，是可以量化的。专家能设计度量体系来评估质量趋势、识别风险信号、驱动改进 |
| **核心框架** | 四类度量：过程度量（用例通过率/自动化覆盖率/需求覆盖）、结果度量（Bug 密度/漏测率/线上故障率）、效率度量（测试周期/回归效率/Bug 平均修复时间）、健康度量（质量趋势/风险热力图） |
| **AI 怎么问** | "我有以下测试数据：[数据]，请帮我分析质量趋势，识别异常信号，给出改进建议" |
| **验收 checkist** | 度量是否覆盖了：过程 / 结果 / 效率 / 健康四个维度；是否有明确的改进行动 |

#### 6.4 `qa-testability-advocacy` — 可测试性推动

| 内容 | 说明 |
|------|------|
| **解决的问题** | 系统设计时没考虑可测试性，测试阶段才发现"这个测不了" |
| **专家经验** | 在架构评审阶段就能识别可测试性问题，推动开发做可测试设计：接口可 Mock、日志可追踪、配置可动态、状态可查询 |
| **核心框架** | 可测试性检查：接口层（是否有 Mock 点、是否有测试接口）、数据层（数据是否可构造/可清理/可隔离）、日志层（关键路径是否有日志、是否有 traceId）、配置层（功能开关/超时时间/阈值是否可动态配置）、依赖层（外部依赖是否有 Mock 方案/是否有降级策略） |
| **AI 怎么问** | "以下是系统架构描述，请做可测试性评审，列出不可测试或难以测试的点，并给出改进建议" |
| **验收 checkist** | 是否覆盖了：接口 / 数据 / 日志 / 配置 / 依赖 五个维度的可测试性 |

### 簇 7：沟通传承（Communication & Legacy）

> 这是天花板能力里的"影响力"部分——一个人的能力再强，如果不能影响团队，天花板就在那里了。

#### 7.1 `qa-stakeholder-communication` — 干系人沟通

| 内容 | 说明 |
|------|------|
| **解决的问题** | Junior 不知道跟不同角色怎么说——跟开发说技术细节、跟 PM 说风险、跟老板说业务影响 |
| **专家经验** | 同样一个 Bug，跟不同人说完全不同的表述方式。核心原则：说对方关心的，而不是你关心的 |
| **核心框架** | 三类沟通模式：**跟开发说**（精确的复现步骤 + 日志/截图 + 根因推测，不用讲业务影响）、**跟 PM 说**（用户影响 + 严重程度 + 修复优先级 + 对其他功能的阻塞）、**跟老板说**（业务影响 + 发布风险 + 建议决策 + 要什么资源）。**高危表达**（绝对不能说的 vs 可以说的） |
| **AI 怎么问** | "我有一个质量风险：[描述]，请生成分别给开发/PM/老板的三版沟通文案" |
| **验收 checkist** | 沟通是否针对受众定制了信息 / 是否包含了对方需要的决策信息 |

#### 7.2 `qa-code-review-for-test` — 测试视角的代码评审

| 内容 | 说明 |
|------|------|
| **解决的问题** | Junior 只看功能测试，不看代码变更，漏掉代码层面的风险 |
| **专家经验** | 有经验的测试会在 CR 阶段看代码，不是为了 Review 代码质量，而是：判断变更影响范围、识别需要重点回归的区域、发现潜在的边界/异常路径 |
| **核心框架** | 测试视角的 CR 四看：看 diff（改了哪些文件、新增/删除了什么逻辑）→ 看影响（变更波及哪些调用方、数据流向哪里）→ 看风险模式（有无静态数据变化、有无超时/重试、有无异常吞没）→ 生成测试建议（哪些需要回归、哪些需要新增用例） |
| **AI 怎么问** | "以下是代码变更的 git diff，请从测试角度分析：影响范围、需要回归的功能、潜在风险、建议新增的测试场景" |
| **验收 checkist** | 是否识别了变更影响范围 / 是否发现了代码级风险 / 是否有明确的测试调整建议 |

#### 7.3 `qa-team-coaching` — 团队赋能

| 内容 | 说明 |
|------|------|
| **解决的问题** | 团队里 Junior 多，资深忙不过来，每个人都在问"这个怎么测" |
| **专家经验** | 授人以渔：把经验做成 checkist、把案例做成模板、把评判标准量化 |
| **核心框架** | 四种赋能方式：**Checklist 式**（把常见测试点做成 checkist，新人照着查）、**模板式**（用例模板/报告模板/Bug 模板，降低输出门槛）、**Review 式**（结构化 Review 流程，不是挑刺而是教学）、**Pair 式**（结对测试时的引导技巧） |
| **AI 怎么问** | "我需要给新人培训 [主题] 测试，请帮我设计一个培训大纲和配套练习" |
| **验收 checkist** | 赋能产出是否可复用 / 是否降低了 Junior 的求助频率 / 是否形成了持续更新的资产库 |

#### 7.4 `qa-retrospective` — 复盘与经验沉淀

| 内容 | 说明 |
|------|------|
| **解决的问题** | 每次漏测都是"下次注意"，但下次还是漏 |
| **专家经验** | 复盘的目的是把"个人经验"转化为"组织资产"。不只是找谁背锅，而是找到系统性的改进点 |
| **核心框架** | 复盘五步法：收集数据（所有 Bug、漏测、线上故障）→ 根因分析（5 Whys，归因到流程/信息/思维/工具）→ 改进措施（具体可执行，不是"加强测试"）→ 资产沉淀（更新 checkist、补充用例模式、改进流程）→ 跟踪闭环（下次怎么确认改进了） |
| **AI 怎么问** | "以下是本次迭代的测试数据和故障信息，请帮我做复盘分析，归类根因，输出改进措施和 checkist 更新建议" |
| **验收 checkist** | 根因是否归到了系统层面而非个人层面 / 是否有可落地的改进措施 / 是否有资产沉淀到 checkist 或规范中 |

## 实施建议

25 个技能是完整蓝图，不用一次性全做。按 ROI 分三个批次：

### 第一批（立刻见效，降低 AI 使用门槛）
```
簇4 全部（AI 协作）× 4 个
+ 簇3 的 heuristic-checklist（启发式清单，效果最直接）
+ 簇1 的 question-framework（让 Junior 知道该问什么）
= 6 个技能
```

### 第二批（建立专业深度）
```
簇2 全部（需求→模型）× 3 个
+ 簇3 剩余 × 3 个
+ 簇1 剩余 × 2 个
= 8 个技能
```

### 第三批（天花板能力）
```
簇5 全部 + 簇6 全部 + 簇7 全部
= 11 个技能
```

## 和其他 Skill 方案的区别

| 维度 | 通用测试 Skill | 这套方案 |
|------|--------------|---------|
| 覆盖范围 | 测试技术 | 思维 + 设计 + AI 协作 + 沟通 + 策略 + 传承 |
| AI 结合 | 无或简单提及 | 每个技能含"AI 怎么问"模块，AI 协作独立成簇 |
| 专家经验编码 | 无 | 启发式规则、思维框架、盲区补偿 |
| 技能联动 | 独立 | 输出→输入串接，有明确 workflow |
| 对 Junior 友好度 | 需要自己消化 | 拆成具体可执行的 checkist + 模板 |
