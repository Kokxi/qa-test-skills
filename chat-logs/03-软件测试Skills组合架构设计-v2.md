# 软件测试 Skills 组合架构设计 v2

> 基于用户反馈重构：解决 AI 辅助测试下"问得浅、产出泛、需反复迭代"的核心痛点。
> 目标：将资深测试经验编码为可继承的技能，让测试人员不再依赖"人手教"。

---

## 核心理念

```
传统培训：       高手告诉新人 → 新人记住 → 下次自己用
Skills 化：      高手经验 → 可加载技能 → AI + 人共同使用 → 稳定输出高质量结果
```

每个技能回答三个问题：
1. **人应该想什么？** — 思维框架和决策模型
2. **AI 应该怎么问？** — 提示词模式：如何给 AI 上下文、如何引导 AI 产出深度
3. **怎么知道够了？** — 验收 checklist：AI 输出有没有漏

## 技能间数据流（联动关系）

```
需求文档/PRD
    │
    ▼
qa-req-deconstruction ──────────→ 输出：需求解构表（显性需求 + 隐性需求 + 风险点）
    │
    ▼
qa-scenario-tree ──────────────→ 输出：场景树（主路径 + 分支 + 异常 + 数据流）
    │
    ├──→ qa-boundary-analysis ──→ 输出：边界清单（输入边界 + 状态边界 + 时间边界 + 依赖边界）
    ├──→ qa-combination-test ───→ 输出：组合矩阵（参数组合 + 环境组合 + 简化策略）
    └──→ qa-business-flow ─────→ 输出：业务流程覆盖图（状态转换 + 跨模块流向 + 数据一致性）
    │
    ▼
qa-ai-context-build ──────────→ 打包以上所有输出，构建 AI 上下文包
    │
    ▼
qa-ai-prompt-catalog ──────────→ 选择对应提示词模板 + 注入上下文 → 生成
    │
    ▼
qa-ai-review ─────────────────→ 评审 AI 输出：漏了什么？不够深？追问还是调整上下文？
    │
    ├── ← 迭代循环：review 不过 → 回退到 prompt 或 context 调整
    │
    ▼
qa-gap-analysis ──────────────→ 对照历史缺陷、checklist、风险模型，找最终遗漏
    │
    ▼
qa-retrospective ─────────────→ 复盘：这次漏了哪里？什么原因？怎么补进下次的 checkist？
```

## 各技能详细定义

---

### 第 0 层：思维基座（底层能力，贯穿所有环节）

#### 1. `qa-critical-thinking` — 测试批判性思维

| 维度 | 内容 |
|------|------|
| **解决的问题** | 测试人员拿到需求后不知道从哪切入，只会跑主流程 |
| **人该想什么** | 每个"正常"背后都有"不正常"：登录成功 → 登录成功但token丢了？重复登录？并发登录？ |
| **核心框架** | 5W1H + "如果...会怎样" + 逆向思维 + 边界质疑 |
| **AI 怎么问** | 给 AI 一个具体需求，要求它按"正向流程→反向流程→异常场景→衍生场景"四层输出 |
| **怎么知道够了** | checklist：是否覆盖了正常/异常/边界/逆向/并发/依赖/环境 |

#### 2. `qa-risk-perception` — 风险感知与优先级

| 维度 | 内容 |
|------|------|
| **解决的问题** | 测试人员对风险不敏感，重要的没深测、不重要的花大量时间 |
| **人该想什么** | 这个功能挂了会发生什么？影响多少用户？有什么补偿机制？ |
| **核心框架** | 影响面 × 发生概率 = 风险等级。功能风险 + 变更风险 + 集成风险 + 数据风险 |
| **AI 怎么问** | 给 AI 需求描述 + 业务背景，让 AI 按"风险类型→影响评估→建议测试深度"输出 |
| **怎么知道够了** | 是否识别出高风险区域并分配了足够测试资源 |

---

### 第 1 层：分析建模（从需求到结构化的测试模型）

#### 3. `qa-req-deconstruction` — 需求解构

| 维度 | 内容 |
|------|------|
| **解决的问题** | 看不懂需求背后的完整边界，漏测 |
| **人该想什么** | 显性需求写了什么？没写但隐含了什么？前后矛盾在哪？不同用户角色的理解差异？ |
| **核心框架** | 需求三层次：显性 → 隐性 → 衍生。输入/操作/状态/输出/规则五维拆解 |
| **AI 怎么问** | "请对以下需求做深度解构，列出显性要求、隐性假设、潜在矛盾、缺失信息" |
| **产出** | 需求解构表（需求ID、显性描述、隐性假设、风险点、疑问） |
| **联动** | 解构表 → 场景树（qa-scenario-tree） |

#### 4. `qa-scenario-tree` — 场景树构建

| 维度 | 内容 |
|------|------|
| **解决的问题** | 用例零散不成体系，想到一个测一个 |
| **人该想什么** | 用户从哪开始到哪结束？中间岔路有哪些？走不通怎么办？ |
| **核心框架** | 主路径 → 分支路径 → 异常恢复路径 → 数据流向。用树结构组织 |
| **AI 怎么问** | "基于以下需求解构，构建完整场景树，按主路径→分支→异常→数据流分层，每层列出具体场景" |
| **产出** | 场景树（结构化文档/思维导图） |
| **联动** | 场景树 → 边界分析 / 组合测试 / 业务流（三路并行） |

---

### 第 2 层：深度设计（从场景到具体的测试设计方法）

#### 5. `qa-boundary-analysis` — 边界与异常深度分析

| 维度 | 内容 |
|------|------|
| **解决的问题** | AI 只给出最浅的边界（比如输入框最大长度），但真正的 Bug 往往在"看起来不是边界"的地方 |
| **人该想什么** | 不只是输入边界，还有：状态边界（从A状态到B状态的临界点）、时间边界（超时/并发/时序）、依赖边界（上游返回值在临界值）、资源边界（内存/磁盘/网络刚好不够） |
| **核心框架** | 四维边界模型：输入边界 → 状态边界 → 时间边界 → 资源/依赖边界 |
| **AI 怎么问** | "对以下场景，按四维边界模型分别列出边界条件：输入边界、状态边界、时间/时序边界、资源/依赖边界" |
| **特别设计** | 这个技能专门解决"AI 想不到深层次边界"的问题，给 AI 喂框架让它按维度推理 |
| **产出** | 边界清单（按四维分类，标注风险等级） |

#### 6. `qa-combination-test` — 组合测试策略

| 维度 | 内容 |
|------|------|
| **解决的问题** | 参数多环境多，全组合测不完，不测又怕漏 |
| **人该想什么** | 哪些组合是真正有价值覆盖的？哪些组合是无关的？哪些参数只要独立测？ |
| **核心框架** | 正交实验简化 + 风险加权组合 + pairwise 策略 + 历史缺陷驱动的组合加权 |
| **AI 怎么问** | "列出以下参数的所有取值组合，先用 pairwise 简化，再标记高风险组合需要额外覆盖" |
| **产出** | 组合矩阵（标注必测组合 + 可裁减组合 + 简化策略） |

#### 7. `qa-business-flow` — 业务流与状态转换测试

| 维度 | 内容 |
|------|------|
| **解决的问题** | 单接口/单页面测试都能过，业务流一起跑就崩 |
| **人该想什么** | 数据在模块间怎么流转？状态怎么转换？什么操作会破坏数据一致性？跨系统的交互点在哪里？ |
| **核心框架** | 状态机建模 → 状态转换覆盖 → 跨模块数据流追踪 → 并发冲突分析 |
| **AI 怎么问** | "对以下业务流程，构建状态转换图，列出所有合法转换、非法转换、边界转换，标注状态持久化点" |
| **产出** | 状态转换图 + 跨模块数据流图 + 一致性检查点清单 |

### 第 3 层：AI 协作（这是最核心的特色层）

#### 8. `qa-ai-context-build` — 测试上下文构建

| 维度 | 内容 |
|------|------|
| **解决的问题** | 测试人员上来就让 AI "生成用例"，AI 没有上下文只能输出通用货 |
| **人该想什么** | AI 需要知道什么才能产出好用例？业务背景？技术架构？风险偏好？历史缺陷？ |
| **核心框架** | 上下文七要素：业务描述 + 需求解构 + 场景树 + 技术架构要点 + 历史缺陷模式 + 测试偏好 + 输出格式要求 |
| **关键技巧** | 知道什么时候给多、什么时候给少。给少了 AI 泛泛，给多了 AI 迷失重点——要用结构化方式喂 |
| **AI 怎么问** | 不直接问"生成用例"，而是先组织上下文包，再基于上下文提问 |
| **产出** | 上下文包（结构化的 AI 输入模板） |
| **联动** | 把第 1-2 层的产出打包成上下文 → 喂给 AI → 用后面两个技能引导 |

#### 9. `qa-ai-prompt-catalog` — 测试提示词模板库

| 维度 | 内容 |
|------|------|
| **解决的问题** | 测试人员不知道怎么问 AI 才能产出深度用例，每次都在试错 |
| **人该想什么** | 不同的测试目标需要不同的问法：探索边界用一种问法、覆盖路径用另一种、风险评估又是一种 |
| **核心框架** | 提示词模式分类：上下文构建式、分步引导式、角色扮演式、反向追问式、checklist 校验式 |
| **典型模板（示例）** | "你是一个有 X 年经验的 [领域] 测试专家。以下是一个 [功能] 的完整上下文：... 请按以下框架输出：[框架要求]。" |
| **产出** | 提示词模板数据集（分类 + 适用场景 + 示例） |
| **联动** | 从 catalog 选模板 → 注入 context（qa-ai-context-build） → 生成 → review |

#### 10. `qa-ai-review` — AI 输出评审与补全

| 维度 | 内容 |
|------|------|
| **解决的问题** | AI 生成的用例看起来"都对"，但总感觉少了点什么——你不知道少了什么，它也不会主动说 |
| **人该想什么** | AI 的盲区在哪？它没问你的背景信息？它假设了什么？它的输出密度够不够？ |
| **核心框架** | 六维评审法：完整性（有没有覆盖场景树）、深度（边界够不够深）、风险（高风险区是否深挖）、一致性（有没有矛盾）、可实现性（能不能测）、冗余度（有没有无价值用例） |
| **AI 怎么问** | "以上输出中，哪些场景你假设了未提供的上下文？请列出所有假设。然后按六维评审法逐条评价" |
| **迭代策略** | 如果不满意，不要重新开始问，而是定向追问：在第 X 点上深入一层 / 补充 Y 类场景 / 按 Z 角度重新审视 |
| **产出** | 评审报告（遗漏点 + 假设清单 + 改进方向） |
| **联动** | review 不过 → 回到 context 或 prompt 调整（qa-ai-context-build / qa-ai-prompt-catalog）→ 重新生成 |

### 第 4 层：复盘与沉淀（持续改进）

#### 11. `qa-gap-analysis` — 测试缺口分析

| 维度 | 内容 |
|------|------|
| **解决的问题** | 测完了，但怎么知道测够了？还有没有漏的？ |
| **人该想什么** | 对照什么标准检查遗漏？历史同类型 Bug 模式有哪些？变更影响范围是否全部覆盖？ |
| **核心框架** | 三维对照法：对照场景树查覆盖缺口 + 对照历史缺陷模式查盲区 + 对照变更影响分析查关联影响 |
| **AI 怎么问** | "基于以下场景树、已设计用例和历史缺陷库，分析测试缺口，按风险等级排序" |
| **产出** | 缺口分析报告（已覆盖 / 部分覆盖 / 未覆盖，附带风险评级） |

#### 12. `qa-retrospective` — 复盘与能力沉淀

| 维度 | 内容 |
|------|------|
| **解决的问题** | 每次漏测都不知道怎么补，下次还是漏 |
| **人该想什么** | 这次漏测的根本原因是什么？是思维盲区、信息缺失、还是流程问题？怎么把它变成 checkist 补充？ |
| **核心框架** | 5 Whys 根因分析 → 分类归因（思维/信息/流程/工具）→ 改进措施 → checkist 更新 |
| **AI 怎么问** | "以下为本次漏测的 Bug 清单，请进行根因分析归类，并建议如何补充测试 checkist" |
| **产出** | 复盘报告 + 更新的 checkist/资产库 |
| **联动** | 复盘产出补充到 qa-gap-analysis 的对照基准中，形成闭环 |

## 三条实施路线（选哪个都行）

### 路线 A：从痛点最大的地方切入

> 适合先解决"AI 生成太浅"这个最疼的问题

```
qa-ai-context-build → qa-ai-prompt-catalog → qa-ai-review
    ↓（效果不好再往下补）
qa-req-deconstruction → qa-scenario-tree → qa-boundary-analysis
```

### 路线 B：从思维改造开始（扎根）

```
qa-critical-thinking → qa-risk-perception → qa-req-deconstruction
    → qa-scenario-tree → 任意设计技能 → AI 协作层
```

### 路线 C：全量按层次推进

```
第 0 层 → 第 1 层 → 第 2 层 → 第 3 层 → 第 4 层
（每层内部可并行）
```

## v1 到 v2 的关键变化

| v1 | v2 | 原因 |
|----|----|------|
| 按生命周期组织 | 按 AI 协作工作流组织 | 更贴合实际使用场景 |
| 14 个技能 | 12 个技能 | 合并冗余，聚焦核心痛点 |
| 工具类技能（JMeter/Selenium） | 思维+方法类技能 | 工具替换快，思维不过时 |
| AI 只是简单提及 | AI 协作单独成层（3 个技能） | 这是最大的差异化价值 |
| 技能独立 | 技能间有明确数据流和联动 | "下一个该做什么"有指引 |
| 通用检查 | 每个技能有"AI 怎么问"和"怎么知道够了" | 减少对资深人员的依赖 |
